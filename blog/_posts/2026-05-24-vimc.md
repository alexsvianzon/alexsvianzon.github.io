# Introduction

I recently took the time to start working more in the terminal, using Vim as my primary editor, and building a terminal clock in C. I had a lot of fun with this project, experienced many hurdles, and learned a lot about the tools I used. In this article, I want to reflect on what happened along the way and what I got out of it.

# Starting With Vim

I had used Vim a few times before this, and never bothered with customization. I quickly found a more suitable editor for me, Visual Studio Code, and didn't look back. But, as I continued using it, I found it to be almost too much. That isn't to say I don't like the editor, I really enjoy the ecosystem it provides. But, I wanted a more hands-on experience. And the terminal provides just that. But switching to the terminal would mean changing editors. Now, I have been using a Raspberry Pi a lot recently (Which I may have a blog post on), and that meant I was using the `nano` editor on Linux. But, I ultimately chose Vim for the acclaimed speedy editing.

I started out with pretty much a blank slate, and tried editing a simple file, which went as good as you can expect for someone who barely remembers the commands. Eventually, I found my way to the `.vimrc`, and tried my hand at customization. I used some of the basics, like syntax highlighting, line numbers and relative line numbers, expand tab, and ignore case when searching. I also customized some of my keybinds. I set my leader key to the space bar, and everything followed from there. I set some simple Vim commands to combos of `<leader><letter>` like w/q/x/u for file operations, h/j/k/l for switching between splits, and e for NERDTreeToggle. Speaking of NERDTree, I also installed vim-plug as a plugin manager for Vim. I installed NERDTree so I could see my project directory and switch between files faster. I also installed LightLine. To be honest, LightLine hasn't been that useful to me. However, I am learning about customizing it and want to get my git status onto it soon. Besides that, it does make it easier to understand my statusline and it does not tank performance like others do.

Beyond customization, I've learned a lot about what Vim provides automatically. Early on, I barely understood Visual mode. But now, I totally get why people need it. Even V-Block. Say you have an array of arrays, and only want to get the first item from each inner array. You'd use V-Block to select that portion. Have I ever needed to use it like that? No, but understanding it and having a theoretical use for it is good enough for me.

# The Terminal Clock

With Vim readily prepared, I took on a simple task: a terminal clock in C. First, I had to determine how I would achieve the look of a changing clock without repeatedly printing to the terminal. I landed on using `ncurses`. It uses ANSI codes to tell the terminal where to draw characters instead of traditional line-by-line printing. I worked on the clock while I edited my Vim experience. I would try a keybind or a new setting for a little, and would tweak it if needed.

I started with a time getter, using `time.h` from the C standard library for functions like `strftime` and `localtime`. After I made sure I could get the correct time, I moved onto getting `ncurses` to work, and simply figuring it out proved to be the bulk of the project. I was able to get a static screen that stayed persistant until stopping the application. Because I wanted the time to be readable from a glance, I needed ASCII characters. Now, I originally was considering something like a FIGlet font. But, it would require a lot more setup and I didn't need all the characters. So, I just made my own character set of the digits and a colon (:). Now, I had to print these characters to the terminal. This was a fairly easy step, mainly because I had already figured out how I would need to print the characters. After that, printing the time to the terminal and updating it was done. Last, I wanted to make it so that the clock would only quit when the user presses 'q.' Unfortunately, polling for a key press every frame does take up CPU resources. So, I added a small rest with the `napms()` function.

# A Quick Word About My Shell

Being in the terminal more was a great experience, but there were a few platform tools that improved it even more. When I heard about Nushell, it really interested. The idea of a data oriented shell intruiged me. So, I decided to download it and try it out. Right away, I discovered what "data oriented" meant. Being able to visualize file formats like JSON, YAML, or SQLite is super helpful if I don't want to open a text editor. Having a way to sort through the output of a command like `ls` is helpful as well. Tables, which come out of both of these things are also really well implemented and makes it easer to read info. The error messages are also very verbose right out of the box, which makes understanding why I got a command wrong easier. One issue I had with Nushell setup was getting it to recognize commands I may have downloaded through Homebrew or system commands. I had to configure my Nushell editor to configure Nushell, and there were a lot of directories to add. But Nushell wasn't my only tool. I also installed Starship, a cross-shell prompt. It makes working with my projects easier. I can get into the right headspace about which language I'm using, my git status, and command completion. It's a subtle tool, but makes writing code a lot easier.

# Conclusion

All in all, there were a lot of good things that came out of this project. I got to practice writing in C, really learn Vim, and I got a terminal experience that was truly mine.
